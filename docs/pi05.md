# Official OpenPI / π₀.₅ integration

Robot-vLLM uses the third-party `openpi-client` package from
[Physical-Intelligence/openpi](https://github.com/Physical-Intelligence/openpi),
pinned at `215abfb217dbac7d5f1273282331b9b1866c0479`. Install with
`pip install -e '.[pi05]'`. The dependency is the upstream client subpackage;
no training code or model weights are downloaded by this extra. Python 3.10–3.12
is recommended because the upstream client currently requires NumPy < 2.

`OpenPiClient` invokes the official `WebsocketClientPolicy.infer()` method and
its NumPy/MessagePack serialization. A small connection-lifecycle override bounds
connection/receive waits and closes each completed call's connection. This avoids
the upstream client's indefinite connection retry and prevents consuming an old
response after a timeout. It does not define a second inference protocol.

Connection and receive timeouts raise `ProviderTimeout` (a `ProviderError`
subclass); the HTTP bridge reports 504. Other client/transport failures report
502. Metadata and inference receive waits are each bounded by `timeout_s`,
so this is a per-operation limit, not a single end-to-end deadline. A timed-out
connection is closed; a subsequent request opens a new connection. The bridge
does not retry a failed inference automatically.

## DROID profile

The profile is specific to `pi05_droid`, not arbitrary Pi 0.5 checkpoints.
The upstream source of the mapping is
[`examples/droid/main.py`](https://github.com/Physical-Intelligence/openpi/blob/215abfb217dbac7d5f1273282331b9b1866c0479/examples/droid/main.py)
and [`droid_policy.py`](https://github.com/Physical-Intelligence/openpi/blob/215abfb217dbac7d5f1273282331b9b1866c0479/src/openpi/policies/droid_policy.py).

| Input | Runtime source |
| --- | --- |
| `observation/exterior_image_1_left` | Configured exterior RGB camera, letterboxed to 224×224 |
| `observation/wrist_image_left` | Configured wrist RGB camera, letterboxed to 224×224 |
| `observation/joint_position` | Seven measured joint positions in the declared order |
| `observation/gripper_position` | Measured aperture mapped to the declared DROID open/closed convention |
| `prompt` | GPT-6 node instruction, or the task instruction |

Neither camera is fabricated when absent. State dimensions, order, numeric values
and gripper calibration are checked before inference. The no-hardware quickstart
explicitly supplies synthetic observations; production adapters do not silently
substitute them.

The model returns an `N×8` action chunk. The first seven values are normalized
joint-velocity inputs in the upstream DROID example; the eighth controls gripper
position. They are not a joint-position vector. The operator declares velocity
scales, sample period, arm joint limits and gripper calibration in
`configs/pi05.droid.json`. The bridge dispatches a short prefix through a group of
native arm `FollowJointTrajectory` and gripper `GripperCommand` capabilities.

The arm path integrates velocity using `q_next = q_measured + velocity × scale × dt`.
This is a position-trajectory bridge and requires controller-specific commissioning;
it does not reproduce DROID's native velocity controller automatically. Configured
clipping is explicit. Gripper output is thresholded at 0.5 as in the upstream
example; a transition ends the prefix so the next round uses fresh observations.
The service never infers hardware scales from an array's length.

Pi 0.5 does not return a task-success head. The bridge's `done` means the declared
number of policy chunks has been consumed. Manipulation success remains an
independent evaluation or higher-level observation/decision concern.

## Serving and endpoint identity

The full OpenPI model server runs separately, normally on a GPU host. Launch its
`serve_policy.py` with `pi05_droid` and an actual checkpoint; see README commands.
The local `robot-runtime-pi05` bridge exposes the runtime's JSON VLA node contract
while using the official client to contact that server. Multiple robot mappings
can share one bridge; request admission is bounded by `max_concurrency`.

The bridge's `model` field identifies its configured target. Upstream server
metadata does not necessarily authenticate the loaded checkpoint. A configured
endpoint or an echoed name alone is not evidence of pretrained inference; verify
the model server and checkpoint separately. A service failure never falls back to
a synthetic policy.

## Checks performed

Both `robot-runtime quickstart` and `robot-runtime quickstart --transport ros2`
have completed the two-robot, two-chunk-per-robot flow and a dependent service call.
The client implementation is the actual pinned upstream package. Default policy
responses and robot observations are explicit fixtures, not pretrained inference.
The tests additionally check native-client invocation, message shapes, bounded
metadata waits, velocity integration, gripper transitions, camera keys, joint order,
and rejection of missing/non-finite state.

Real checkpoint performance and physical multi-arm task outcomes are not claimed.
Existing experiments can supply an OpenPI endpoint without changing the DAG,
resource coordinator, ROS device contracts or recovery state machine.
